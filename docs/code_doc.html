COD 导航栈代码详解

福州大学 RM 队暑期任务。本文档逐文件、逐函数说明四个包的代码：cod_referee_interfaces（消息）、cod_referee_simulator（裁判模拟+键盘）、cod_decision_bt（决策行为树）、cod_sim（PRIEST 局部规划器）。

先看这张图：整个系统的两条链路。键盘改状态 → 行为树决策 → 导航执行。

系统架构与数据流

四个包分三层职责：消息定义（包1）→ 模拟与决策（包2、3）→ 执行（包4 + Nav2）。

包 1 · cod_referee_interfaces

纯消息包（rosidl），三个消息定义了裁判系统数据的结构。行为树的条件节点和裁判模拟器都依赖它。

msg/GameStatus.msg

src/cod_referee_interfaces/msg/GameStatus.msg
游戏阶段
uint8 STAGE_PREPARATION = 0   # 准备阶段（上场前）
uint8 STAGE_SELF_CHECK  = 1   # 自检阶段
uint8 STAGE_RUNNING     = 2   # 比赛进行中
uint8 STAGE_GAME_OVER   = 3   # 比赛结束

uint8 stage             # 当前阶段（用上面的常量）
int32 stage_remain_time # 本阶段剩余秒数

消息常量 STAGE_* 在 C++/Python 里可以直接用：cod_referee_interfaces::msg::GameStatus::STAGE_RUNNING。行为树 IsGameRunning 判断 stage == STAGE_RUNNING。

包 2 · cod_referee_simulator

模拟 RoboMaster 裁判系统：一个节点维护游戏阶段和机器人状态，一个键盘节点改状态。行为树读这两个状态做决策。

src/referee_simulator_node.cpp

src/cod_referee_simulator/src/referee_simulator_node.cpp
裁判系统模拟器（状态机）

内部状态

stage_          // 当前阶段（PREPARATION/SELF_CHECK/RUNNING/GAME_OVER）
remain_hp_      // 当前血量
ammo_count_     // 弹丸数
heat_           // 热量
stage_time_left_// 当前阶段剩余秒数
max_hp_ / max_ammo_ / heat_limit_  // 上限（参数）

timer_callback() —— 每秒推进

  1. 阶段倒计时 stage_time_left_--
  2. 按阶段流转：PREPARATION 到点 → SELF_CHECK；SELF_CHECK 到点 → RUNNING（重置血/弹/热）；RUNNING 里热量每 1s 降 5，血量归零或超时 → GAME_OVER 并退出节点
  3. 每轮 publish_status() 发布两个话题

cmd_callback() —— 键盘指令

指令处理
1~4切阶段（设置对应阶段和倒计时）
5remain_hp_ = max(0, remain_hp_-100)
6ammo_count_ = max(0, ammo-20)
7heat_ = min(heat_limit, heat+40)
8重置：血量满、弹满、热量 0
9remain_hp_ = min(max_hp, remain+100)（回血）

publish_status()

把内部状态填进 GameStatus + RobotStatus 发布到 /referee/game_status 和 /referee/robot_status。

包 3 · cod_decision_bt

nav2 风格的行为树：5 个自定义 BT 插件节点 + 一个独立跑树的节点。核心思路——决策逻辑写进 XML，条件/动作节点是纯逻辑，状态从裁判话题读，导航交给 nav2 标准节点。

nav2 BT 插件机制回顾：BehaviorTree.CPP 用插件库注册自定义节点。每个节点类有 providedPorts()（定义端口）和 tick()（执行逻辑）。一个库文件里用 BT_REGISTER_NODES(factory){...} 注册多个节点，编译时加 BT_PLUGIN_EXPORT 让 BT_RegisterNodesFromPlugin 符号导出。运行节点用 BehaviorTreeEngine 加载插件库 + XML。

条件节点 1：IsGameRunning

include/cod_decision_bt/conditions/is_game_running_condition.{hpp,cpp}
游戏是否 RUNNING

构造函数

从黑板取 node（rclcpp 节点句柄），订阅 /referee/game_status，回调里缓存最新阶段（加互斥锁保护）。构造订阅而不是 tick 里订阅，避免每 tick 重建。

tick()

if (!data_received_) return FAILURE;   // 没数据 → 保守失败
return stage == STAGE_RUNNING ? SUCCESS : FAILURE;

端口

game_status_topic默认 /referee/game_status

条件节点 2：IsHpLow

include/cod_decision_bt/conditions/is_hp_low_condition.{hpp,cpp}
血量比例是否低于阈值

tick()

// 回调里算好 hp_ratio = remain_hp / max_hp（max_hp>0 时）
if (!data_received_) return FAILURE;
double threshold = 0.3;  // 从端口读
return hp_ratio_ < threshold ? SUCCESS : FAILURE;

端口

threshold默认 0.3（血量低于 30% 触发）
robot_status_topic默认 /referee/robot_status

动作节点 1：SetRetreatGoal

include/cod_decision_bt/actions/set_retreat_goal_action.{hpp,cpp}
把补给点坐标写黑板 goal

SyncActionNode（同步动作，tick 立即完成）。从 XML 的 x/y 端口读坐标，构造 PoseStamped（frame=map），写到黑板 goal。后续 NavigateToPose 读这个 goal 发给 bt_navigator。

为什么硬编码：之前用 TF 动态取"出生点"（树启动时缓存），但缓存时机不稳（TF 瞬态/车已跑远）反复出错。改成 XML 硬编码 0.2, 0.3（出生点附近）最可靠。想改补给点直接改 XML。

端口

x / y补给点坐标（当前 0.2 / 0.3）
frame_id默认 map

动作节点 2：StopRobot

include/cod_decision_bt/actions/stop_robot_action.{hpp,cpp}
原地停车

构造时创建 /cmd_vel 发布者；tick 发 0 速度。用于"游戏未开始 / 健康待命"分支。发 0 是保险，因为车本来就没导航指令。

cmd_vel_topic默认 /cmd_vel

动作节点 3：PatrolNextWaypoint

include/cod_decision_bt/actions/patrol_next_waypoint_action.{hpp,cpp}
选下一个巡航点写黑板

parse_waypoints()

把 "x,y; x,y; ..." 分号分隔的字符串解析成坐标列表（去空白、按逗号拆分）。

tick()

// 第一次时解析 waypoints
auto [wx, wy] = waypoints_[index_];       // 取当前巡航点
index_ = (index_ + 1) % waypoints_.size(); // 循环前进
// 默认 use_spawn_pose=false：直接用绝对坐标
goal.x = wx; goal.y = wy;
写黑板 goal; return SUCCESS;

use_spawn_pose=true 时坐标是"相对出生点的偏移"（从黑板 spawn_pose 读出生点加偏移），当前 XML 用绝对坐标所以没用到。

巡航点不"跳太快"的原因：XML 里 PatrolNextWaypoint 后面跟着 NavigateToPose。Sequence 会记住正在 RUNNING 的子节点，导航期间不会重跑 PatrolNextWaypoint，到点后才取下一个。

decision_tree_node.cpp

src/cod_decision_bt/src/decision_tree_node.cpp
决策树运行节点（独立跑树，不依赖 bt_navigator 也能 tick）

参数

bt_xml决策树 XML 路径（launch 注入）
plugin_libraries要加载的插件库列表（自定义 + nav2 的 NavigateToPose）
bt_loop_duration_ms100（tick 周期）
server_timeout_ms / wait_for_service_timeout_msaction 服务超时

try_create_tree() —— 初始化

  1. 创建 BehaviorTreeEngine，加载所有插件库（含 nav2_navigate_to_pose_action_bt_node）
  2. 初始化黑板，键与 bt_navigator 一致：node（节点句柄）、bt_loop_duration、server_timeout、wait_for_service_timeout、goal(空 PoseStamped)
  3. 从 XML 建树 → BT::PublisherZMQ 开 1666 端口（Groot 实时监控）→ 启动 tick timer
  4. 创建失败（如 bt_navigator 未就绪导致 NavigateToPose 的 action client 连不上）→ 0.5s 后重试

tick_tree() —— 每 100ms

auto status = tree_.tickRoot();   // tick 整棵树
if (BT::StatusCompleted(status))   // 树跑完一个决策周期
  bt_engine_->haltAllActions(root); // 复位所有节点，下一 tick 重新决策

behavior_trees/decision_tree.xml

src/cod_decision_bt/behavior_trees/decision_tree.xml
决策树本体
<ReactiveFallback name="MainDecision">
  <!-- 分支1 游戏未进行 → 停车 -->
  <Sequence name="IdleNotRunning">
    <Inverter><IsGameRunning/></Inverter>
    <StopRobot/>
  </Sequence>

  <!-- 分支2 血量低 → 回补给点 -->
  <Sequence name="RetreatToSupply">
    <IsHpLow threshold="0.3"/>
    <SetRetreatGoal x="0.2" y="0.3"/>
    <NavigateToPose goal="{goal}"/>
  </Sequence>

  <!-- 分支3 正常 → 巡航 6 点 -->
  <Sequence name="Patrol">
    <PatrolNextWaypoint waypoints="5.2,0; 4.3,-6.3; 9.8,-6.5; 9.9,-0.5; -0.2,-6.1; 0.2,0.3"/>
    <NavigateToPose goal="{goal}"/>
  </Sequence>
</ReactiveFallback>

每个节点的角色

节点类型作用
MainDecisionReactiveFallback根决策器：从左到右试分支，高优先级成立就打断切换
IdleNotRunning 等Sequence分支内动作全成功才算成功
Inverter装饰器取反：IsGameRunning 失败 → 成功（即"游戏没在跑"）
NavigateToPoseAction（nav2）把黑板 goal 发给 bt_navigator 的 /navigate_to_pose，导航中保持 RUNNING
ReactiveFallback 为什么适合做决策

每个 tick 重新从左到右评估。巡航中血量掉低 → 分支2 条件成立 → 立刻打断分支3 的导航（取消 nav goal）转回补给点。优先级和互斥由树结构保证，不用写 if-else。

包 4 · cod_sim（仿真 + PRIEST）

PRIEST 是论文算法（Projection Guided Sampling，IEEE RA-L 2024），用伯恩斯坦多项式参数化轨迹，采样 + 投影到可行域 + CEM 迭代优化。这里把它接入 ROS2 当局部规划器（替代 MPPI）。

priest_bridge.py · 回调

odom_cb() —— 更新位姿

从 Odometry 读 x,y,vx,vy，并从四元数算 yaw（atan2 公式）。

goal_cb() —— rviz 2D Goal

  1. rviz 目标是 map 系，PRIEST 用 odom 系，用 TF odom→map 转换（target = goal + trans.translation）
  2. path_odom = None：清旧路径（防新目标路径没到就沿用旧路径走错方向）
  3. has_target = True
  4. 调 _request_global_path() 向 planner_server 请求全局路径

_request_global_path() → _path_goal_done() → _path_result_done()

用 ComputePathToPose action 异步请求全局路径。起点用 TF 把当前位姿转到 map 系。结果回调里把路径点转回 odom 系存到 path_odom。

js_cb() —— 读 gimbal_yaw

从 joint_states 里找 gimbal_yaw_joint 的角度。

_parse_cloud() —— 手动解析 PointCloud2

不用 sensor_msgs_py，直接用 struct.unpack_from 按 field offset 解 x,y,z，省 Python 库开销。

cloud_cb() —— 点云 → 障碍

  1. TF 把点云从传感器系转 odom 系
  2. 过滤：0.15 < dist < obs_range（0.15 下限保留贴身点；雷达本身 ~0.4m 内测不到，见调参记录）
  3. 降采样到 420 个，不足补 100.0（远离标记）
  4. 存 x_obs / y_obs

priest_bridge.py · 控制循环

control_loop() —— 15Hz timer

  1. 算法未初始化：调 _init_algorithm()（JIT 编译 ~30s，期间车不动）
  2. 无目标：发 0 速度停车（等 rviz 2D Goal）
  3. 有目标但路径未就绪：发 0 速度（避免直冲目标切弯，等全局路径）
  4. 到目标 <0.4m：发 0 速度停车
  5. 贴障碍 <0.35m：推离最近障碍（兜底，防物理卡死）
  6. 算 PRIEST 输出 → 按 gimbal_yaw 旋转到 gimbal_fake 系 → 发布 /priest_cmd
为什么输出要旋转：MPPI 输出是 gimbal_fake 系（底盘控制器按 gimbal_yaw 旋转到底盘系后车才走对方向）。PRIEST 算的是 world/odom 系，要先转 +gimbal_yaw 到 gimbal_fake 系，再经 fake_vel_transform + chassis_controller。

priest_bridge.py · 计算

_init_algorithm() —— 建算法 + JIT 预热

self.prob = mpc_expert.batch_crowd_nav(
    a_obs=1.0, b_obs=1.0, v_max, v_min, a_max,
    num_obs=420, t_fin=1.5, num=100, num_batch=110,
    maxiter=1, maxiter_cem=30,
    weight_smoothness, weight_track, way_point_shape=1000, v_des)
self._compute_step(0,0,0,0)   # 触发 JIT 编译（~30s）

关键参数：a_obs/b_obs=1.0（避障椭圆）、t_fin=1.5（时间域）、maxiter_cem=30（CEM 迭代）。

_compute_step(x,y,vx,vy) —— 一次控制计算

  1. waypoint：有全局路径用 _path_waypoints，否则直线到目标
  2. 初速度：v_init = min(v_des, dist_to_end/t_fin) 沿 waypoint 方向 → 轨迹内建自然减速
  3. path_spline：路径弧长参数化
  4. compute_warm_traj：温启动轨迹（含近终点缩短）
  5. compute_obs_traj_prediction：障碍轨迹预测
  6. compute_traj_guess：初始猜测（含投影）
  7. compute_cem：CEM 迭代优化（核心）
  8. compute_controls：从最优轨迹前 0.45s 提速度
  9. v_max 截断 → 返回 world 系速度
v_init 与弧度耦合：初速度小（靠近目标时）→ 轨迹需从低速加速 → 平滑代价高 → 偏爱弧线；初速度大 → 轨迹直。这就是"速度减慢后回到弧线状态"的原因。近终点弧度另靠"轨迹长度缩短"控制。

mpc_expert.py · 矩阵初始化

src/cod_sim/cod_sim/priest_algo/mpc_expert.py
类 batch_crowd_nav

伯恩斯坦多项式

# 10 阶伯恩斯坦基，在 [0, t_fin] 上采 num=100 个点
self.P, self.Pdot, self.Pddot = bernstein_coeff_order10(...)
# 轨迹 = P @ c（c 是 11 个系数，nvar=11）
# 位置=P c, 速度=Pdot c, 加速度=Pddot c

约束矩阵

矩阵含义
A_eq等号约束：起始位置/速度/加速度 + 终点位置（边界条件）
A_vel = Pdot速度不等式约束
A_acc = Pddot加速度不等式约束
A_obs = tile(P, 30)障碍投影约束（30 个最近障碍）

投影代价矩阵

cost_x_projection = rho_proj·A_projᵀA_proj + rho_obs·A_obsᵀA_obs
                   + rho_ineq·A_accᵀA_acc + rho_ineq·A_velᵀA_vel
cost_mat_x_projection = [[cost_x_projection, A_eqᵀ],[A_eq, 0]]

投影本质是个 带约束的最小二乘，预先求逆（cost_mat_inv_x_projection）在 GPU 上批量解。

采样协方差

用二阶差分矩阵构造轨迹的平滑先验协方差，multivariate_normal 采样初始轨迹。

mpc_expert.py · 投影（避障核心）

把采样轨迹"推"到可行域

compute_projection() —— 投影 QP

b_obs_x = x_obs + d_obs·cos(alpha_obs)·a_obs   # 目标：椭圆边界上的点
lincost_x = -rho_proj·A_projᵀ·b_proj - lambda - rho_obs·A_obsᵀ·b_obs - ...
sol = cost_mat_inv_x_projection · [-lincost, b_eq]   # 解 QP

initial_alpha_d() / compute_alph_d_proj() —— 交替最小化变量

障碍用极坐标表示（d_obs 视线距离、alpha_obs 角度）：

alpha_obs = atan2(ws·a_obs, wc·b_obs)      # 轨迹点相对障碍的角度
d_obs = c2_d / c1_d                          # 视线距离
d_obs = max(1, d_obs)   # ← 论文的 d≥1：轨迹必须推出椭圆外
a_obs 为什么不能太大：a_obs=2.5 时投影把轨迹推到 2.5m 侧绕，CEM 权衡后放弃绕行选穿障碍 → 撞上。a_obs=1.0 既有足够绕行弧度又能避让。

mpc_expert.py · 代价函数

compute_cost_batch()

dist_obs = 1 - (dx/a_obs)² - (dy/b_obs)²   # 椭圆方程：>0 表示在椭圆内
cost_obs = ||max(0, dist_obs)||             # 轨迹点穿透椭圆的惩罚

cost_smoothness = ||xddot|| + ||yddot||     # 加速度（平滑）
cost_track      = ||x - x_project|| + ...   # 到路径的横向距离
cost_length     = ||diff(x)|| + ||diff(y)|| # 路径长度（抑制弧线）

cost_batch = 1.0·res_norm + 0.25·smooth + 3.0·track
           + 12.0·cost_obs + 2.0·length

各项作用：res_norm 投影残差（轨迹离可行域多远）；smooth 惩罚急加速；track 让轨迹贴全局路径；cost_obs 避障；length 直线最短。

近终点轨迹缩短（jnp.where）

# compute_warm_traj 和 compute_traj_guess 里
remaining = arc_vec[-1] - arc_point         # 剩余路径弧长
look_ahead = v_des·t_fin·0.5                # 正常前瞻 1.875m
look_ahead = jnp.where(remaining < look_ahead·2,
                       remaining·0.5, look_ahead)  # 近目标缩短一半
# 效果：轨迹随接近平滑缩短 → 没空间弧 → 近终点更直
关键坑：这两个函数带 @partial(jit)。里面不能用 Python if（对 traced 值），否则 JAX 报错 → 桥卡死不发布。必须用 jnp.where。
